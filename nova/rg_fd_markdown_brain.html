三題

1. 夠不夠、哪裡撐不住。 速度不是瓶頸（rg 掃 Linux kernel 7.5 萬檔 0.08 秒，webkimi 引 BurntSushi 基準）。撐不住的三點，webclaude 與 webkimi 各自獨立給出同樣三點：

  • 「載入」先於「搜尋」撐不住：agent 要知道有什麼得先讀一份索引。Karpathy 說幾百頁、Anthropic 說 CLAUDE.md 200 行、OpenClaw 的 MEMORY.md 超過預算就截斷。門檻是塞進 context 的那份索引，不是檔案數。
  • 字面查得到、語意查不到：「commit ab3f2c1」rg 贏；「我對架構的看法演變」rg 要人下同義詞。
  • 寫入紀律：jayzeng 1,000+ session 的結論是「session 記錄做了什麼，memory 是對下一個 agent 該知道什麼的判斷」。沒有機制逼 agent 寫得可搜，檔案就變垃圾場。這是純檔案路線真正的死因，跟規模無關。

2. 跟資料庫式比。 各席都指出同一個訊號：qmd、OpenClaw、ai-memory、beads 全部把檔案當真相、資料庫當可重建的索引。「可讀、可 diff、可攜」是各陣營共識，差別只在檢索層疊什麼。向量贏在同義與跨語言、輸在精確符號與可稽核性，而且要養模型（qmd 三個 GGUF 約 2GB，中文要換 embedding）；SQLite FTS 是甜蜜點（rg 的一切加排名，索引壞了重建）；圖譜贏在關係查詢、輸在 agent 寫錯 frontmatter 就是壞資料。

3. 最省事組合。 webclaude 與 webkimi 獨立推出同一套：純 markdown 目錄＋git＋rg／fd＋一份 200 行以內的索引檔（OpenClaw 三檔佈局或 Karpathy index.md）；超過幾百頁才裝 qmd（一條 collection add，檔案一個不動，Claude Code／pi／OpenClaw 三種 agent 共用同一索引）。不選 basic-memory／memsearch，因為它們的價值建立在 agent 寫對 frontmatter 或外部向量庫上；多席多廠商的環境，寫入規則越少越活得久。

Sai 的獨立評估（不是任何一席的話）

  • Nova 現況是兩套並存：gbrain（真相住 PGLite，向量＋FTS）與 Claude Code 的 memory 目錄（MEMORY.md 索引＋rg 掃逐字稿）。跟主流差的一格是 gbrain 的真相不住檔案，PGLite 停機打不開就要 export 重建，正是「索引不可重建」那種痛。
  • 三個撐不住的點裡，我們已經撞過兩個：MEMORY.md 索引膨脹（prompt-audit 已建議合併）、寫入紀律（memory 檔越寫越像流水帳）。第三個（語意落差）由 gbrain 的向量層在補。
  • 這輪沒有決策。Ray 的原話是假設，顧問室的答案是「成立，附三個條件」。要不要把 gbrain 的真相搬回 markdown 檔案，是另一題。
